## 实际执行证据

两组原生实验在[隔离Linux CI](https://github.com/CaptainGreenskin/infra-guide/actions/runs/42471646629)运行，原生源提交为`f9e86bc18e320ed808f88c60bf961232cb79fc65`。本机没有Docker daemon，没有启动用户的Docker Desktop或接触已有数据库。镜像固定到已核对的官方版本与摘要，程序只清理自己的随机命名资源。

- etcd 3.6.16实际运行三成员：多数侧提交42，孤立旧成员允许陈旧读取时仍是37，最新读/写失败；重连追平，失去多数再恢复写43。旧快照恢复为独立新集群后先读37，重新列举、从R+1接续watch，接到47事件后更新缓存，再用完整读取逐项核对。没有把“旧watch被取消”冒充缓存已经重建。
- MySQL 8.4.13实际运行两个实例：RR同连接110/110、提交后130；RC130/135。暂停应用后，源142、副本新查询135，接收和应用集合分别检查。切换先停止旧业务写、冻结G₂，再核对候选；目标额外GTID只允许复制前实际采集的可信初始化集合B，不事后豁免整个来源UUID。硬停旧实例后新端写到145，余额和每笔回执独立验收。
- 官方mcp 2.3.0、Python3.12实际运行三个stdio服务端进程。2026-07-28版逐请求声明元数据；2025-11-25兼容路径单独初始化。实际消息关联请求、进度和取消；取消后关闭处理器文件，同一连接继续读5，EOF后核对进程回收。结构合法且isError=false的41仍被独立来源42拒绝。

原生调试也修正了真实接口问题：MySQL复制选项按官方语法；SHOW状态通过XML解析保留多来源GTID换行；初始化事务在复制开始前单独留证。失败原始记录保留在作者输出目录，最终记录与固定源码摘要绑定，未把失败执行写成通过。
