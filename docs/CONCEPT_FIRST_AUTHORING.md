# 面向中文初学者的内容编写规则

先让读者知道有哪些对象、怎样相互作用，再让读者推导机制。目录、领域页与章节都遵循这条顺序。术语表只处理局部缺口，不能代替连续讲解。

## 依赖顺序

1. **定义对象**：用一两句说明它是什么、保存什么或负责什么。缩写首次用于推理时，给出中文含义与作用。
2. **连接对象**：说明谁产生输入、谁持有状态、谁执行、谁确认结果。先后、包含、控制与依赖关系分开。
3. **推导机制**：在已经介绍的对象上增加条件，解释正常过程及失败过程。一个段落回答一个主要问题。
4. **走通例子**：沿一组输入、数值或事件一直算下去。图、公式和代码用同一套名称和假设。
5. **改变条件**：只改变一个关键条件，预测结果，再用独立判据检查。面试追问回到这一步。

前置依赖确实较长时，先用一句话补足当前推理所需含义，再给前置章节。不能让读者必须离开当前页查五个词，才能读懂第一段。章节标题可以点题，正文第一段不应该继续堆尚未解释的词。

## 三条主线的起点

- Cloud：程序 → 进程与服务 → CPU、内存、存储、网络 → 云提供资源 → 服务模型与责任 → 虚拟化、网络、数据、编排、交付与可靠性。
- AI：输入与模型 → 参数、训练与推理 → 词元编号与向量 → 模型计算 → 损失、梯度与更新 → GPU执行 → 多进程并行、恢复与服务。
- Agent：任务与完成条件 → 模型提议 → 运行时检查与安排 → 工具实际执行 → 状态与回执 → 验收 → 恢复、权限、记忆、检索与评估。

这是组织依赖的骨架。进入某个细分章节时，仍需补足该章节最小的概念起点，不能假设读者严格按全站顺序读完。

## 词语必须放回语境

“节点”可能是机器、计算图中的运算或追踪中的一次操作；“索引”可能是数据库结构，也可能是数组位置；“上下文”可能是模型输入或追踪传播信息。“激活”也可能指中间数值或非线性变换。不能给这些词套统一替换。

重复定义要克制：前文已经清楚说明的词，后文直接使用。新增解释不得插入代码、命令、字段名、路径、链接或图注。`pool-limit`、`CPU.limit`、`"GPU":3` 等内容保持原样。代码和完整实验的源文件继续是可核对的事实来源。

## 图怎样参与解释

- 讲组成：层级或包含图，标明对象与边界。
- 讲调用：顺序图，标明发起方、执行方、结果及丢失窗口。
- 讲资源：预算表、堆叠图或时间线，写清单位、寿命与并发条件。
- 讲计算：张量形状、数值矩阵或数据依赖图，指出每个输入来自哪一步。
- 讲取舍：固定假设的对照图；实验记录与概念示意分别标注。

箭头要说明方向和含义。不能在同一条未标注的线里混用请求、资源依赖和参数更新。新图中的专业词也要先定义，不能借图引入另一批未解释概念。

## 如何验收一章

作者从读者角度顺读：每个新名词能否回到本页前文定义，或就地说明？每一条因果能否指向已介绍的对象？公式能否手算？代码能否按说明运行？结果能否由独立判据确认？

自动检查负责覆盖、链接、锚点、源码一致性和已知反例；它不能证明“普通人已经读懂”。后续读者试读应记录卡住的原句、缺失概念及一次复述或练习结果，不以点击或自评勾选代替掌握。
