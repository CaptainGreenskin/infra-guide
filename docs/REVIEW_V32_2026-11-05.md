# 第32轮：存储接口、TP 反向与 Kairo 验收讲到可核对

本轮选择三篇尚无图解、关键机制仍能深入的章节。保留已有知识主线，增加责任图、实际计数图、链式法则图、前向槽图和验收时序，配三份独立完整程序。累计24篇不同章节实质完善：Cloud9、AI7、Agent7、共享1。全站仍为66章与95点，没有把目录任务数当章节数。

## 存储：接口、粒度、版本与样本身份

三列责任图先分对象、文件、块的命名、布局、共享和发布责任。将串行成本改成带单位的公式与表：10000个64KiB样本共625MiB，固定每请求5ms、125MiB/s；逐样本55秒，百样本分片5.5秒。这是声明模型，保留并发、压缩、缓存和随机访问会改变结论的边界。

新程序用独立小夹具启动实际本机HTTP：20个64字节样本，每4个组成分片，选0/1/6/7/17。整分片带本次请求内缓存，3次成功请求、768B响应体；索引Range为5次、320B；两路交付相同320B样本。服务端另记录3+5请求。三个实际反例分别是旧清单遇到对象变化返回412、错误索引偏移导致样本摘要不符、越界范围416。

读范围不能直接拿片段摘要对整对象摘要。新正文解释版本、ETag条件、对象摘要与样本/块摘要的作用；夹具用SHA256作ETag，不推广为真实S3规则。已重新阅读S3 GetObject与对象完整性官方文档，正文就近引用。小实验不测试云存储、压缩、响应头总量或性能。

## TP：不仅前向要合并，输入梯度也要算全

开篇改为定义→FFN→逐元素激活→分片。第三节小尺寸仍与前两节明确分开。新增完整dU、dH、dW、dX链式法则和矩阵账本：Y=[12,5]、目标[3,−1]、loss58.5、dY=[9,6]；两份dX为[9,6]与[30,36]，合并为[39,42]。

两实际CPU/Gloo进程持有W的两列、U的两行。前向SUM、输入梯度SUM、错误偏置SUM均真实执行；参数梯度及lr0.01的更新与完整模型自动求导基线比较，并另核对手算矩阵。各局部先加偏置再归约实际得到错误[13,6]。ReLU次序反例0与1也实际计算。

普通集合调用明确放在自动求导图外，程序手工把dY传给本地partial.backward；没有将它伪装成生产TP层。只运行两成员CPU组，没有运行8rank的DP/PP/TP坐标、GPU/NCCL或物理多机。流水图另以两等时阶段、四微批展示8/10=80%，仍不是完整训练利用率。

## Kairo：先固定测试者契约，再检查记录

章节更名为“Kairo 接入验收：任务、权限与结果证据”。五种职责分开：用户端、运行时、状态存储、工具服务、独立验收器。只读任务的测试者契约固定A的事件5/7/11、total23、原会话、引用和B版本/摘要；观测记录不能自行改评分答案或权限。

通用程序执行1正例与10个拒绝对照。CLI另用公开JSON夹具复跑错误总数、缺少读、非字符串任务身份与B版本变化；只改来源标签并编一个版本时，记录可以仍相容，但provenance_verified始终false。这一控制明确展示校验器的边界。程序不调用模型、工具后端或Kairo，也不证明记录来源真实性。

时序图使用题设时刻，受理响应丢失在客户端之前终止；不是Kairo运行记录。真实目标表继续保持待接入，通用夹具通过没有改写目标状态。
